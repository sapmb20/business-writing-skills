# Decide whether you have enough context to draft (step 1.6, in full)

Part of `business-writing`. The body of the skill carries the summary; this is the full rule set.

Steps 1.1 through 1.5 either produced what you need or exposed what is missing. Make the
go/no-go call explicitly, before writing a word. Drafting past a gap does not close it — it
buries it in fluent prose, where the user is far less likely to catch it than if you had
simply asked.

**The test.** For each thing you don't know, ask: *would two plausible answers produce
materially different drafts?*
- **No** — assume the likeliest answer, note it, and draft.
- **Yes, but it is a discrete fact** such as a date, a name, or a number — bracket it as
  `[start date]` and draft. List the brackets on delivery.
- **Yes, and it changes the framing, the claims, the tone, or the structure** — stop and ask.
  This is the only case that blocks drafting.

**Never infer these. Ask.**
- **What the interaction actually was.** A conversation can be an interview, a screening
  call, an informational chat, an orientation, or a favor to whoever made the introduction.
  Each produces a different email. The label the user reaches for — "my interview" — is
  often not what happened, so ask what was discussed and who did most of the talking.
- **How the relationship started:** cold outreach, a formal application, or an introduction.
  A referral changes what the reader already believes about the writer, and it attaches a
  third party's standing to how the writer behaves.
- **Who the other recipients are** and what they do, whenever there is more than one.
- **What has already been said.** Never reconstruct a thread from the user's summary of it.
- **The size and shape of the downside,** and what the user is optimizing for: speed,
  warmth, precision, or a durable record. These pull against each other, and guessing wrong
  produces a draft that is well written and useless.

**Ask for the artifact, not a summary.** When a thread, a job posting, a prior draft, or a
document exists, ask the user to paste it rather than asking five questions about it. One
paste answers more than the questions would, and it answers in the other party's own words
instead of the user's recollection of them.

**Ask once, and ask well.**
- Batch every question into a single round. Four or five is the ceiling.
- Say in a clause why each one matters, so the user can tell which are load-bearing.
- **Offer the default you would use for each,** so the user can decline to answer and still
  get a draft: "If you'd rather not dig those up, say so and I'll assume X and flag it."
- Don't open a second round unless an answer revealed a genuine fork.

**Don't over-fire.** The gate exists to stop confident drafting on invented context, not to
turn every task into a questionnaire.
- Never ask about anything that has a sensible convention or default.
- Scale it to the stakes. A short note to someone the user knows well needs no gate at all.
  A first contact, an offer thread, a message that creates a record, or anything with real
  downside gets the full test.
- Anything the user has already told you anywhere in the conversation is not an open question.
- Every message counts, and waiting for better preparation is not always better. When the
  cost of delay exceeds the cost of a small gap, bracket the gap and send.

**When you proceed on inference, say so.** If a load-bearing belief about the relationship,
the process, or what was previously said came from your own inference rather than from the
user, name it in one line on delivery, so it can be corrected before the piece is sent. An
inference stated plainly is cheap to fix. The same inference buried inside a confident
sentence is not.
